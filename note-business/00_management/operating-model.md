# 事業運営モデル（体制・権限・PDCA）

最終更新: 2026-11-07 / 作成: 事業責任者（Claude）

## 1. 体制と役割

| 役割 | 担当 | 責任 | 主な権限 |
|---|---|---|---|
| オーナー | あなた | 事業の最終責任、noteアカウントの保有・公開操作、売上受取、確定申告 | 事業継続/撤退、ジャンル変更、予算、公開可否の最終判断 |
| 事業責任者 | Claude | **成果（KPI）への責任**、計画立案、エージェントへの指示と品質保証、意思決定の記録 | ジャンル選定、商品設計、価格（承認済みレンジ内）、制作計画、改善施策 |

| 企画エージェント | サブエージェント | キーワード調査、記事企画（ブリーフ）、編成カレンダー | — |
| 執筆エージェント（複数） | サブエージェント | 無料記事・有料記事の原稿作成、修正 | — |
| 編集・コンプラ審査エージェント | サブエージェント | 品質スコアリング、事実確認、法令・規約チェック | 公開NGの判定 |
| 読者パネルエージェント | サブエージェント | 想定読者ペルソナとしての購買意向評価 | — |

> エージェントは原稿・分析などの「制作物」までを担い、**外部への公開・発信・課金設定はオーナーが行います**（Claudeはnoteアカウントにログインできず、無断で外部発信もしないため）。

### 階層型の体制（2026-11-07 オーナー承認）

エージェントは必要に応じて配下にサブエージェントを作り、並列化してよい。

```
オーナー
 └─ 事業責任者（Claude）……成果責任・意思決定・最終品質保証
     ├─ 調査チーム（各調査担当 → 論点別サブエージェント）
     ├─ 制作チーム：編集長 → ライター複数（記事ごとに並列）
     ├─ マーケティング担当（プロフィール・SNS・見出し画像）
     └─ 審査チーム：編集・コンプラ審査／読者パネル　※制作チームとは別系統
```

運用ルール:
- **職務分離**: 制作したエージェントが自分の成果物を最終審査しない（審査チームは独立）。
- 配下を作るリーダーは、分担範囲・採点基準・共通ルール（非公開APIの回避禁止、出典明記、git操作禁止など）を明文化して渡し、成果物を統合・検証してから事業責任者に報告する。
- コミット・プッシュは事業責任者のみが行う。

## 2. PDCAは2層で回す

```
【社内PDCA：公開前】1サイクル＝数時間〜1日
  Plan  企画（需要・競合・差別化の確認）
  Do    執筆（複数ライター並行）
  Check 編集・コンプラ審査＋読者パネル評価（スコア化）
  Act   修正・制作テンプレート/チェックリストの改善 → 次の企画へ反映

【市場PDCA：公開後】1サイクル＝1週間（月次で大きな見直し）
  Plan  今週の仮説と施策（例：タイトル改善、価格テスト、新記事）
  Do    公開・SNS投稿（オーナー）
  Check noteダッシュボードの数値（PV・スキ・売上）をKPI表に記録
  Act   事業責任者が分析→次週の施策と制作指示を決定
```

## 3. 品質ゲート（通過しないものは公開しない）

| ゲート | 判定者 | 合格基準 |
|---|---|---|
| G1 企画 | 事業責任者 | 想定読者と悩みが具体的／検索需要か購買の兆候がある／競合より優れる点を1文で言える |
| G2 原稿 | 編集・コンプラ審査 | 品質スコア80点以上、コンプラ重大指摘0件、事実関係を確認済み |
| G3 公開前 | オーナー | 実体験や実績の偽装がない／自分の名前で出して問題ない内容か |

## 4. オーナーへのエスカレーション基準

事業責任者が単独で決めず、オーナーに**提案（推奨案つき）**する事項:
1. お金・個人情報・時間に関わること（予算、アカウント情報、身元の開示、運用時間）
2. 法的・規約上のリスクが残る判断
3. 外部への公開・発信の実行そのもの
4. 撤退・大きなピボット（ジャンル変更など）

上記以外（企画、制作、品質、改善施策）は事業責任者が決定し、`decision-log.md` に記録します。

## 5. 使用量の上限（2026-11-09 オーナー依頼、2026-11-13 に80%へ変更）

このプロジェクトが使うのは、Claudeの5時間枠の**80%まで**とする（残りはオーナーの他の用途のため）。

| ルール | 内容 |
|---|---|
| 計測 | `05_operations/tools/usage-guard/usage.py` で、このプロジェクトの使用量を5時間枠ごとに集計する。過去に上限へ達した6回の使用量（ばらつき±9%）の中央値を容量100%と推定する |
| エージェントの自己停止 | 作業の区切りごとに `usage.py --quiet --check 70` を実行し、70%以上なら保存して停止する |
| 監視役 | バックグラウンドで2分ごとに使用率を確認し、75%に達したら事業責任者に通知 → 稼働中のエージェントを即座に停止する（区切りまでの超過を防ぐ） |
| 新しい起動を控える | 事業責任者は、使用率60%以上ではエージェントを新しく起動・再開しない |
| 同時に動かす数 | 最大2体 |
| 起動の仕方 | 大きな作業記録を持つエージェントの再開は高くつく（記録の読み直しで枠の10〜15%）。必要な資料だけを渡した新しいエージェントを優先する |
| 再開 | ガードで止めたときは、その枠のリセット時刻に1回だけ再開を予約する。安全網として6時間ごとの自動チェックを置く（チェック自体も60%以上なら何もしない） |
| 目安の引き下げ（2026-11-14） | 80%ガードでも、通知から停止までの間と事業責任者自身の読み直しで超えたため、新規起動55%未満・自己停止65%・監視役70%に下げた |
| 週間の上限（2026-11-14 オーナー依頼） | このプロジェクトは週間容量の**70%まで**。`usage.py` の週間メーターで管理する（容量は、11/9に週間上限へ達するまでの使用量から推定）。エージェントは `--check-week` で自己停止。1日の目安は、メーターが出す「残りの予算（1日あたり）」 |
| 事業責任者の消費 | 時間を空けて動くたびに、長い会話の読み直しで5時間枠の7〜13%を使う。動く回数を減らし、必要なら新しいセッションに引き継ぐ（`00_management/handoff.md`） |
| 限界 | 公式の計器ではなく推定。オーナーが同じ枠・同じ週に他で使った分は含まない。週の区切りは推定 |
