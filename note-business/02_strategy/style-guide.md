# 文体ガイド：「AIっぽさ」を減らす（v1.0）

決定: 事業責任者（Claude）／2026-11-13（D-016）
根拠: `01_research/ai-likeness-research.md`（市場の言説24件の分析、信頼に関する研究、当社11本の診断）

## 1. 方針

1. **人間を装わない。** AI活用の開示は維持する。体験として書けるのは検証ログ（`03_content/verification/`）にある事実だけ。わざとの誤字、キャラクターの演出、架空の体験、AI検出の回避は採らない。
2. **消すのは「型・繰り返し・内部用語」。** 当社の記事のAIっぽさは、定番のAI表現（11本の無料部分で0件）ではなく、検証報告書のような口調にある。具体的には、「結論：」「まとめ：」のラベル見出し、同じ注意の繰り返し（19件）、丸かっこの多さ（比べたnote記事の3倍以上）、制作工程の言葉。
3. **判断の足跡を前に出す。** 何を試し、何が起き、何を変えたか。これは他のAI記事との差であり、売り物の「検証済み」の証拠になる。研究でも、AI作成の開示で信頼が下がる原因は「人の監督なしにAIが全部書いた」と受け取られることにある。人が何をどう確かめたかを具体的に書く。

## 2. 文体ルール S1〜S15（ビフォー・アフターは調査レポート §6.2）

| # | ルール |
|---|---|
| S1 | 1文目は場面から書く。「〜向けの記事です」「この記事では〜を紹介します」と記事が自分を説明しない |
| S2 | 見出しは結論の文にする。「結論：」「まとめ：」のラベルと、全記事共通の骨組みを使わない |
| S3 | 制作工程の言葉（「執筆とは別の新しい実行」「独立実行」）を使わない。検証のやり方は読者の言葉で1記事1回だけ書く（例：「記事を書いた会話とは別の新しい会話で2回試した」） |
| S4 | 同じ注意（出力の揺れ、他のAIは未検証、保証しない）は1記事1回。冒頭の検証情報か末尾の定型文に置く |
| S5 | 丸かっこの補足は1段落に1つまで。曜日・関数の引数を除き、1,000字あたり4つ以下を目安にする |
| S6 | 範囲の宣言（「この記事では〜しません」）は「扱わないこと」の1か所に集める |
| S7 | 「ないこと」の宣言を「あること」の事実に置き換える |
| S8 | 「〜ことがあります」「可能性があります」は、検証で起きた回数に置き換える（例：「16回中12回で」） |
| S9 | 1文は60字以内。80字を超えたら切る（URLは数えない） |
| S10 | 見出しの丸かっこ補足は記事全体で2つまで |
| S11 | 判断の足跡（試したこと→起きたこと→変えたこと）を前半に1つ置く。検証ログにある事実だけ |
| S12 | 検証情報と開示は「AIが何を作り、人が何をどう確かめたか」を具体的に書く |
| S13 | 定番のAI表現（patterns.json の warn）を使わない |
| S14 | 同じ文末は3文まで。4文目は形を変える |
| S15 | 文例・プロンプト（コードブロック）は、実務の文書として自然かどうかで判断する。過剰な敬語と念押しだけを直す |

## 3. 既存ルールの調整（content-guidelines・writing-format-spec より優先）

- 「出力例はClaudeで生成。AIの出力は毎回少しずつ変わります」「ChatGPT・Gemini・Copilotは未検証」は、**1記事1回**（冒頭の検証情報）でよい。
- 無料記事の「結論を先に」「まとめ」は機能として残す。ただし見出し名を「結論：」「まとめ：」にしない（S2）。
- 検証情報の書式は、1文目を「いつ、人が何をどう確かめたか」にする（S12）。独立実行による検証は今後も続け、記事での書き方だけS3に従う。

## 4. 編集の手順（5工程）

| 工程 | 担当 | やること | 完了の条件 |
|---|---|---|---|
| 0 書く前 | 事業責任者 | ライター指示書にこのガイドを入れる。気づいた癖は都度ルールに足す | 反映済み |
| 1 機械チェック | ライター／文体編集 | `05_operations/tools/style-lint/` で本文を点検する（コードブロック・メタ情報・末尾の定型文を除く）。丸かっこの密度と80字超の文も数える | warn 0件（残すなら理由を記録）。info は目で確認 |
| 2 AIに指摘だけさせる | ライター／文体編集 | 調査レポート §6.3 のプロンプトを、執筆とは別の会話で実行する。書き換えはさせない | 指摘の一覧が出た |
| 3 人が直す | ライター／文体編集 | 指摘から採るものを選んで直す。足すのは検証ログの事実だけ | 採点4以上の見込み |
| 4 冒頭の音読 | オーナー | 公開前の確認の中で、タイトル・冒頭3段落・見出しだけを声に出して読み、言わない言い回しに印をつける | 印の箇所を直した |
| 5 採点と記録 | 審査担当 | §5で採点し、審査記録に残す | **4以上で公開可** |

## 5. AIっぽさの採点基準（1〜5）

| 点 | 状態 | 機械の目安 | 人の目安 |
|---|---|---|---|
| 5 | 自然。型も繰り返しもない | warn 0、丸かっこ4/1,000字以下、80字超の文0 | 1文目が場面、見出しは結論の文、同じ注意は1回、判断の足跡が前半にある |
| 4 | ほぼ自然 | warn 0、丸かっこ6以下 | 残った info は意図したもの。音読の引っかかりは2〜3か所 |
| 3 | ところどころ型が見える | warn 1〜2、または丸かっこ6〜9 | ラベル見出しが残る、または同じ注意が2回 |
| 2 | 検証報告書調・型どおり | warn 3以上、または丸かっこ9超 | 工程用語が2回以上、同じ注意が3回以上 |
| 1 | AIの出力そのまま | 定番の決まり文句が複数 | 検証ログにない体験・数字が1か所でもあれば、ほかが良くても1 |

## 7. 102の試行結果と手順の改訂（2026-11-13、D-017）

- 結果（`04_review/style-pilot-102.md`）: warn 5→0、info 10→3、丸かっこ 10.7→1.3（1,000字あたり）、80字超の文 2→0、ラベル見出し 2→0、機械の目安 2→5。自己採点4（オーナーの音読が未了のため）。文例・プロンプトは変えていない。AIの指摘24件のうち15件を採用、1件を一部採用、8件を不採用。
- **工程2の改訂**: 指摘させる実行は、Opusでは安全フィルターで2回止まり、失敗だけで枠の約8%を使った。今後は、試行で成功した形（Sonnetを使い、思考・出力・時間に上限を付ける。S13は patterns.json と書かず決まり文句の例で示す）で実行する。コマンドは `04_review/style-pilot-102.md` の工程2の記録を写して使う。
- **S2の補足**: 作業名の見出し（例：「管理表の作り方」）は使ってよい。結論が言える節は結論の文にする。
- 閾値は据え置く。丸かっこの数え方（曜日を除く）と、点数の境目（6/1,000字は4点の上限）を lint の出力に合わせて読む。
- 根拠のない記述の扱い: 検証ログにない一般的な説明（例：エラーの意味）は、検証済みの記事（103など）へのリンクか公式ヘルプの出典を付け、実機での見え方はオーナーの確認項目にする。

## 6. 効果の確かめ方

公開後は、noteの管理画面で取れる指標（ビュー・スキ・コメント・購入数）で、直した記事と直す前の記事を比べる。件数が少ないうちは差が出ても偶然の範囲なので、月単位でまとめて判断する（週次レビューで記録）。
